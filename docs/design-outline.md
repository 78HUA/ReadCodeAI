# ReadCodeAI 设计大纲

> **这份文档是什么**：ReadCodeAI 的**施工图级**设计文档。它同时承担三个职责 ——
> ① 记录设计决策与取舍理由；② 给出可以直接照着开工的架构、数据模型与接口；
> ③ 定义每一步的**可复现验证方式**。
>
> **读者**：项目作者本人（开工与复盘）、以及任何想评估这个项目的人。
>
> **写法约定**：结论先行；涉及取舍的地方必须写清「选了什么、为什么不选另一个」；
> 每个核心设计点附一句「一句话讲法」，方便口头复述。
>
> **更新纪律**：每个阶段（第 0–9 步）完成后，**必须把实测数字回填进本文档**，
> 过期或未经实测的描述不许留在文档里。

## 1. 项目定位

### 1.1 一句话定义

> **给它一个 Java 代码仓库，你可以问「这个功能在哪实现的」「这个方法被谁调用」「改这个签名会影响哪些地方」——它给出答案，每条结论都带「文件 + 行号」证据，而且证据可以被程序化核验。**

它同时能承担**代码审查**：输入一个类或一次改动，输出带证据的审查意见。

### 1.2 为什么做它

| 理由 | 说明 |
|---|---|
| **自己就是用户** | 读陌生开源项目是真实需求，不是编出来的场景 |
| **数据零成本、无限量** | clone 任何一个开源仓库就有了输入 |
| **答案可以自动校验** | 「谁调用了 X」这类问题的正确答案**是程序算出来的**，不需要人工标注（见第 6 章） |
| **演示效果好** | 「那你分析一下我这个项目」——当场就能跑 |
| **不需要重型基础设施** | 起步只需要 MySQL + 一个 LLM API |

### 1.3 判据自检：它够不够格叫「AI 原生项目」

| # | 判据 | 本项目 | 结论 |
|---|---|---|---|
| 1 | AI 是产品本身，不是辅助功能 | 去掉 AI，它就退化成一个 `grep` | ✅ |
| 2 | 输入非结构化、长、人处理不过来 | 几万行陌生代码 | ✅ |
| 3 | 存在证据链能约束模型输出 | **文件路径 + 行号**，比视频时间戳更精确 | ✅ |
| 4 | 能构造有客观正确答案的评估集 | **而且能自动构造、自动判卷**（第 6 章） | ✅ |
| + | 数据拿得到 | clone 就有，零成本、无限量、无合规风险 | ✅ |

### 1.4 能力拼图：它在作品集中补的是哪块

| | 深度优化型项目 | 高并发型项目 | **ReadCodeAI（本项目）** |
|---|---|---|---|
| 定位 | 深度优化（后端性能） | 高并发补充 | **AI / Agent 原生** |
| 展示的能力 | 找问题 + 量化改进 | 并发场景 + 缓存一致性 | **AI 工程：证据约束 + 评估体系** |
| 基础设施 | MySQL/Redis/MQ/ES/ffmpeg | MySQL/Redis/RabbitMQ | **只要 MySQL + LLM API** |

**三者的能力拼图不重叠。** 本项目补的是「AI 工程」这块，也是三者中唯一以「AI 是产品本身」为前提的项目。

> **为什么这里不写另外两个项目的名字**：本仓库是公开的，而「A 项目分析 B 项目」这种关联很容易被读成
> 两个项目互相配套、甚至像结果被安排过。**技术性关联一律切断**（测试语料、示例路径、验证步骤），
> 作品集层面的定位只保留「补的是哪块能力」这一层信息。

### 1.5 目标与非目标

**目标**（按能力列出）：

1. **定位**：「X 功能在哪实现」→ 带文件 + 行号
2. **调用关系**：「谁调用了 X」「X 调用了谁」→ 调用链 + 证据
3. **结构**：「这个类有什么字段/方法」「这个接口有哪些实现」
4. **影响面**：「改这个签名会影响哪些调用点」
5. **多跳推理**：「这个参数从哪来」→ 沿调用链向上追，**跳几跳、什么时候停由模型决定**
6. **结构化摘要**：给一个仓库，先给出「它是干什么的」—— 结构（模块划分、入口、调用枢纽）**由索引算出来**，语义描述由模型补
7. **代码审查**（第二阶段）：对一段代码给出带证据的意见

**非目标**（明确划出来，防止范围蔓延）：

| 不做 | 理由 |
|---|---|
| ❌ 代码补全 | 那是 Copilot 的地盘，且需要编辑器集成 |
| ❌ 第一版支持多语言 | 多语言解析要绑 tree-sitter native，成本高、收益低 |
| ❌ 追求「能回答任何问题」 | **答不了就说答不了**，比瞎编强 |
| ❌ 第一版引入向量库 | 绝大多数问题靠符号表 + 调用图 + 全文检索就能答对，且答案更准（见第 4 章） |
| ⚠️ 前端**排到最后** | 前端是**产品面**，不是可有可无的包装 —— 但要等引擎能力稳定后再做（第 8 步），否则接口每改一次就得重做一遍界面 |

### 1.6 用户操作流程（端到端）

这是产品的完整形态 —— **用户全程在浏览器里操作，不需要碰命令行**：

```
① 添加仓库
   前端三个入口：
     · GitHub 链接        —— 粘贴 URL（公开仓库不需要 token）
     · 服务器本地路径      —— 自托管时最快，零上传成本
     · 上传压缩包 / 目录   —— 部署到远端、拿不到服务器文件系统时用
   → 后台拉取（远程）或定位（本地）→ 索引 → 前端显示进度与统计

② 看仓库概览（索引完成立刻给一份「结构化摘要」）
   · 算出来的部分：模块划分、文件与符号规模、入口类、调用枢纽
     （被调用最多的类）、实现关系、没有任何调用者的类
   · 模型补的部分：每个模块「大致负责什么」的一句话说明
   ⚠️ 摘要里的**数字全部来自索引，不是模型编的** —— 这是本项目总结和
      「把文件塞给模型让它自己看」的根本区别

③ 追问
   「文件上传功能在哪实现的」「谁调用了这个方法」
   「这个参数从哪传进来的」（这一问会沿调用链追好几跳）
   → 每条答案都带【文件 + 行号】证据，**点开就是真实代码**

④ 核对（这一步是产品可信度的来源）
   证据卡片点开显示的是**校验过的真实文件内容**；
   模型编造的路径或行号会被系统拦下、触发重新检索，而不是照原样给你
```

**四个环节缺一不可**：只有 ①③ 就是个套壳问答；加上 ② 用户才知道从哪问起；加上 ④ 才敢信。**②和④是本项目区别于通用 AI 问答的地方。**
| ❌ 重型中间件编排 | 多中间件每样都浅，不如窄而深 |

## 2. 核心设计

> 这一章是整个项目最值钱的部分。六条洞察，每条都附「一句话讲法」。

### 2.1 洞察一：代码理解 ≠ 文档 RAG

常规 RAG 套路是「切块 → 向量化 → 相似度检索」。**但代码有强结构，这套用在这里是浪费。**

| 问题 | 正确手段 | 为什么不是向量检索 |
|---|---|---|
| 「方法 X 定义在哪？」 | **符号表查询** | 这是查表，答案是**确定的** |
| 「谁调用了 X？」 | **调用图遍历** | 这是**图查询**，向量相似度做不了 |
| 「这个接口有哪些实现？」 | **类型层次查询** | 同样是图 |
| 「哪个文件处理文件上传？」 | **全文/关键词检索** | 标识符是**精确 token**，不是语义 |
| 「这个功能**大概**在哪儿实现？」 | 向量检索 | **只有这一类真的需要语义** |

**所以设计是「三层检索 + 按问题类型路由」，而路由本身就是可讲的设计点。**

**一句话讲法**：「代码不是文档 —— 文档是自然语言，要靠语义相似度猜；代码有符号表、有调用图，很多问题是**能算准**的。把能算准的交给模型去猜，是设计错误。」

### 2.2 洞察二：按符号切分，不按行切

按固定行数切分的典型事故：**一个方法被劈成两半**，检索到上半段时模型看不到返回逻辑，于是自信地给出错误结论。

**正确做法：按语言语法结构切。**

| 语言 | 工具 | 能拿到什么 |
|---|---|---|
| Java（第一版） | **JavaParser** | 类 / 方法 / 字段 + 精确位置 + 调用关系 |
| 多语言（后续可选） | tree-sitter | 需绑 native，成本高，**第一版不做** |

每个 chunk 的元数据：

```
{ 文件路径, 起始行, 结束行, 所属类, 方法签名, 修饰符, 内容 hash }
```

**方法签名单独建索引** —— 它是检索时最好的 key（标识符精确、语义密度高）。

**一句话讲法**：「按行切会把一个方法劈成两半，模型看到半段代码就会自信地答错。按符号切，切出来的是完整的方法。」

### 2.3 洞察三：三层检索 + 「能算准的别猜」

| 层 | 手段 | 服务的问题类型 | 是否确定性 |
|---|---|---|---|
| **第 1 层** | 符号表 / 调用图 / 类型层次（静态分析） | 定位、调用关系、结构、影响面 | ✅ **完全确定** |
| **第 2 层** | 全文检索（标识符、字符串常量、注释） | 「哪个文件处理上传」 | ✅ 基本确定 |
| **第 3 层** | 向量相似度 | 「大概在哪实现」这类模糊问题 | ❌ 概率性（v1 不实现，仅预留接口） |

> **纪律：能从第 1、2 层拿到确定答案的问题，不许交给 LLM。**

模型只负责「**选择用哪层、如何组合结果、把多跳结果串成答案**」，不负责「猜事实」。

**一句话讲法**：「能算准的别猜 —— 静态分析能给出确定答案的问题，绝不交给模型。」

### 2.4 洞察四：证据约束与三层校验

每条回答必须带证据，输出契约：

```json
{
  "answer": "文件上传的入口是 FileController.upload()，它调用 UploadService 落盘",
  "evidence": [
    {
      "file": "src/main/java/com/x/FileController.java",
      "startLine": 42,
      "endLine": 58,
      "snippet": "@PostMapping(\"/upload\") public Result upload(...)",
      "why": "上传接口的映射与实现"
    }
  ],
  "refused": false
}
```

**独立校验环节（分三层，成本完全不同）**：

| 层 | 校验什么 | 成本 |
|---|---|---|
| ① | 文件存在吗？行号范围有效吗？ | **100% 程序化，零成本** |
| ② | 那段代码真的存在吗？和模型给的 snippet 一致吗？（含内容 hash 校验） | **100% 程序化（真读磁盘文件比对）** |
| ③ | 那段代码**真的支持这个结论**吗？ | 需要 LLM 判或人工抽检 |

**①② 两层程序化就能拦住大多数编造**（编文件路径、编行号、编代码片段）。这是代码领域比视频理解干净的地方 —— **视频的「时间戳证据」无法程序化核验内容**。

**校验不过 → 定向补检索**（不是笼统重试）：

| 失败类型 | 补检索动作 |
|---|---|
| 文件不存在 | 模型幻觉了路径 → 重新检索，缩小到已索引文件集合内 |
| 行号越界 / 内容对不上 | 用符号表重查该符号的真实位置 |
| 内容 hash 漂移 | 源码已变更 → 重新索引该文件并标注 |

**一句话讲法**：「模型的每条结论都要带文件 + 行号，而这两样东西**程序能直接去磁盘上核对**。编造的行号过不了校验，过不了就定向补检索，不是重试。」

### 2.5 洞察五：多跳检索才是「Agent」的部分

「这个参数从哪来」——单次检索答不了，要**沿调用链向上追**：

```
模型决定：查谁调用了 methodA        →  拿到 3 个调用点
模型决定：其中一个在 serviceB 里，继续往上追  →  拿到上游
模型决定：够了，组织答案（或者：还差一环，再追一跳）
```

**这就是 Agent**：跳几跳、往哪跳、什么时候停，**由模型决定**，不是写死的。

必须有的约束：

| 约束 | 说明 |
|---|---|
| **跳数上限** | `maxRounds`，作为预算的一部分 |
| **每一跳都要带证据** | 否则整条链不算数 |
| **防止绕圈** | 同一条边不重复走（visited edge set） |
| **四维预算** | 循环上限 + 时长 + token + 成本，任一超限即停 |

**一句话讲法**：「单次检索是工具，多次自主检索才是 Agent —— 跳几跳、往哪跳、什么时候停，是模型自己决定的，但被四维预算框住。」

### 2.6 洞察六：评估集可以自动构造（最大差异化）

**核心洞察：在代码领域，很多问题的正确答案是程序算出来的，不是人标的。**

| 题型 | 怎么自动生成 | 怎么自动判卷 |
|---|---|---|
| **定位题** | 随机挑一个方法，问「它在哪定义」 | 比 文件路径 + 行号 |
| **调用题** | 随机挑一个方法，问「谁调用了它」 | 比调用点集合 |
| **结构题** | 问「这个类有哪些方法/字段」 | 比集合 |
| **实现题** | 问「这个接口有哪些实现类」 | 比集合 |
| **影响面题** | 问「改这个方法的签名会影响哪些调用点」 | 比集合 |

**答案来自静态分析（第 1 步建好的符号表 / 调用图），不来自 LLM** —— 所以**没有「用模型判模型」的循环依赖**，这是评估方案可信的前提。

**规模可以做到几百上千条**（脚本自动跑），而同类项目的评测集往往只有个位数。

**一句话讲法**：「代码领域里，很多问题的标准答案是**程序算出来的**，不是人标的 —— 所以我能脚本批量出题、自动判卷，规模上千条，而且答案不来自模型。」

├── evidence/

**为什么不用 ORM**：表结构就是为查询服务的（符号表、边表），SQL 比 JPA 实体映射更直白，也更好讲「我为什么这么建索引」。用 `JdbcTemplate`，无额外依赖。

### 3.3 数据模型

> 9 张表。库名 `readcodeai`。所有表带 `repo_id` 隔离多仓库索引。

**两个关键设计点先说**：

1. **解析不出来的调用要保留**（`call_edge.resolved = 0` + `callee_raw` + `reason`）。
   这是**盲区的诚实记录** —— 静态分析必然有漏（反射、动态代理、Lombok 生成的代码），
   把「没解析出来」和「不存在」区分开，才能如实报告准确率（见第 8 章）。
2. **行号会漂移**：索引建立后源码可能改动 → 所有证据核验都靠**内容 hash 比对**，
   不一致就标注失效并触发重新索引，而不是盲信数据库里的行号。

| # | 表 | 作用 | 关键字段与索引 |
|---|---|---|---|
| 1 | `repo` | 被索引的仓库与总体状态 | `root_path`、`commit_hash`、`file_count`、`total_loc`、`status`(INDEXING/READY/FAILED)、`indexed_at`；唯一键 `(name, commit_hash)` |
| 2 | `source_file` | 源文件清单与解析结果 | `path`、`content_hash`(SHA-256)、`loc`、`parsed_ok`、`parse_error`；唯一键 `(repo_id, path)`，普通索引 `content_hash` |
| 3 | `symbol` | **符号表**：类/接口/枚举/记录/方法/构造器/字段 | `kind`、`name`、`qualified_name`、`signature`、`parent_id`、`start_line`、`end_line`、`modifiers`、`return_type`、`javadoc`；索引 `(repo_id, name)`、`(repo_id, qualified_name)`、`parent_id` |
| 4 | `call_edge` | **调用图**：调用者 → 被调用者 | `caller_symbol_id`、`callee_symbol_id`(可空)、`callee_raw`、`call_line`、`call_kind`(METHOD/CONSTRUCTOR/STATIC/SUPER/LAMBDA)、**`resolved`**、`reason`(REFLECTION/DYNAMIC/LOMBOK/EXTERNAL/AMBIGUOUS)；索引 `caller_symbol_id`、`callee_symbol_id`、`(repo_id, resolved)` |
| 5 | `type_relation` | 继承 / 实现 | `sub_symbol_id`、`super_raw`、`super_symbol_id`(可空)、`kind`(EXTENDS/IMPLEMENTS)、`resolved`、`external`；索引 `sub_symbol_id`、`super_symbol_id` |
| 6 | `chunk` | 按符号切分的检索单元 | `symbol_id`(可空)、`kind`(SYMBOL/FILE_HEADER/IMPORT_BLOCK)、`start_line`、`end_line`、`content_hash`、`content`、`token_estimate`；`FULLTEXT(content)` with ngram 解析器 |
| 7 | `question` | 自动生成的评估题 | `qtype`(LOCATE/CALLERS/CALLEES/STRUCTURE/IMPLEMENTS/IMPACT)、`payload_json`、**`ground_truth_json`**、`generator_version`、`seed`；索引 `(repo_id, qtype)` |
| 8 | `answer_log` | 每次问答的流水（质量与成本） | `question_id`(可空)、`mode`(STATIC/AGENT)、`route_json`、`hops`、`prompt_tokens`、`completion_tokens`、`cost`、`latency_ms`、`answer_json`、`refusal`；索引 `(repo_id, created_at)` |
| 9 | `evidence_check` | 每条证据的校验结果 | `answer_log_id`、`file_path`、`start_line`、`end_line`、`check1_pass`、`check2_pass`、`check3_result`、`mismatch_type`(FILE_NOT_FOUND/LINE_OUT_OF_RANGE/CONTENT_MISMATCH/HASH_DRIFT/OK)、`repaired`、`repair_action`；索引 `answer_log_id` |

**为什么不用图数据库**：调用图查询主要是「直接前驱/后继」和「有限跳数递归」，MySQL 8 的递归 CTE 完全够用，且少一个中间件。

### 3.4 关键流程

**① 索引流程**

```
指定路径/gitUrl
   → 扫描 .java 文件（按 include/exclude 过滤，跳过 target/）
   → 逐个文件：算 content_hash → JavaParser 解析
       ├─ 成功 → 采集 symbol / call_edge / type_relation
       └─ 失败 → source_file.parsed_ok=0 记录 parse_error（不中断整体索引）
   → 按符号生成 chunk（含方法签名索引）
   → 写 repo 统计（file_count / total_loc / symbol_count / 调用解析率）
```

**② 问答流程**

```
问题
   → QueryRouter 判定类型（定位 / 调用 / 结构 / 实现 / 影响面 / 模糊）
   → 第 1 层（能算准的）：直接查符号表 / 调用图 → 得到确定结果
   → 第 2 层（必要时）：全文检索补充候选
   → 组装上下文（按相关性排序 + 截断 + 去重，控制在 token 预算内）
   → LLM 组织答案（必须输出 answer + evidence[]，或 refused）
   → EvidenceVerifier 校验 ①②③
       ├─ 通过 → 返回
       └─ 不通过 → EvidenceRepair 定向补检索 → 重试（受预算约束）→ 仍不通过则拒答
   → 写 answer_log + evidence_check
```

**③ 校验失败后的定向补检索**

```
mismatch_type = FILE_NOT_FOUND     → 在已索引文件集合内重新检索符号名
mismatch_type = LINE_OUT_OF_RANGE  → 用符号表查询该符号的真实起止行
mismatch_type = CONTENT_MISMATCH   → 重新读取该符号当前内容，重新生成证据
mismatch_type = HASH_DRIFT         → 标记该文件需重新索引，并在答案中标注「源码已变更」
```

### 3.6 可降级设计

> **没配 LLM API Key 时，静态分析部分（第 1、2 层检索）必须照常可用** —— 因为它本来就不需要 AI。

| 能力 | 无 Key 时 |
|---|---|
| 索引（符号表 / 调用图 / 类型层次） | ✅ 完全可用 |
| 定位 / 调用者 / 被调用 / 实现类 / 结构 | ✅ 完全可用（纯查询） |
| 全文检索 | ✅ 完全可用 |
| 多跳链路检索（不生成自然语言答案） | ✅ 可用（返回结构化证据链） |
| 自然语言答案组织 | ❌ 需要 LLM |
| 多跳的「跳向决策」 | ❌ 需要 LLM |

**这个设计有个额外好处**：可以清楚地演示「哪部分是 AI、哪部分不是」—— 先不接模型演示定位与调用关系，再打开模型演示多跳，比全程「AI 黑盒」更有说服力。

### 3.7 配置项

```yaml
readcodeai:
  llm:
    enabled: true                                  # false 或 key 缺失 → 降级为 NoopLlmClient
    base-url: ${READCODEAI_LLM_BASE_URL:}
    api-key: ${READCODEAI_LLM_API_KEY:}            # 只从环境变量读，不落配置文件
    model: ${READCODEAI_LLM_MODEL:}
    timeout-seconds: 60
    max-rounds: 3                                  # 多跳预算：轮次
    max-duration-ms: 60000                         # 多跳预算：时长
    max-estimated-tokens: 60000                    # 多跳预算：token
    max-estimated-cost: 0.5                        # 多跳预算：成本
    input-price-per-million: 0                     # 计价参数，用于成本估算
    output-price-per-million: 0
  index:
    max-file-size-kb: 2048                         # 超过则跳过并记录
    exclude-patterns: ["**/target/**", "**/build/**", "**/generated/**"]
  retrieve:
    top-k: 8
    max-context-tokens: 30000
```

**配置加载时即校验**：预算类参数非法（负数、上限为 0）当场失败，不等到运行时才暴露。

## 4. 技术选型与最小依赖

### 4.1 选型

| 用途 | 选型 | 版本 | 理由 |
|---|---|---|---|
| 语言 / 运行时 | **Java** | **21** | 与本机 JDK 21 及求职方向一致 |
| 框架 | **Spring Boot** | **4.1.1**（第 0 步已验证可用） | 与已有项目版本一致；兼容性实测见 `verification-log.md`（含「Boot 4 不支持 Undertow」这条坑） |
| Java 解析 | **JavaParser** | **3.28.2** | 纯 Java 无 native 依赖；能拿到符号、调用关系与精确位置 |
| 存储 | **MySQL** | 8.0.42（本机已有） | 符号表 + 边表 + 递归 CTE 足够；省略图数据库 |
| 数据访问 | **JdbcTemplate** | Boot 自带 | 表结构就是为查询设计的，SQL 比 ORM 映射更直白 |
| LLM | **OpenAI 兼容 HTTP 接口** | — | 手写客户端，供应商可换（不绑 SDK） |
| 工具调用 | **手写 tool-calling 循环** | — | 不引 AI 框架（见 4.2） |
| 接口 | REST + CLI + **Vue 3 前端** | — | REST 与 CLI 是引擎的对外通道（第 1 步起就有）；前端是产品面，**排到第 8 步**——引擎没定型前做界面等于返工 |

### 4.2 明确不引入的（每条都给理由）

| 不引入 | 理由 |
|---|---|
| **向量库**（Milvus/pgvector/Chroma 等） | 第一版绝大多数问题靠符号表 + 调用图 + 全文检索就能答对，**而且答案更准（确定 vs 概率）**。加向量库会引入「用概率手段解决确定问题」的倒退。等真做到「模糊语义查找」那一步再加，并且**要有数据说明它带来了什么提升** |
| **图数据库**（Neo4j 等） | 调用图查询是「直接前驱/后继 + 有限跳递归」，MySQL 递归 CTE 够用，少一个中间件 |
| **AI 框架**（Spring AI / LangChain4j） | 需要的是最简单的 `/chat/completions` + 工具循环，手写 200 行以内；引框架会带来版本兼容风险，且**框架把工具循环藏起来了，反而讲不清「Agent 体现在哪」** |
| **ORM**（JPA/MyBatis） | 见 4.1 |
| **Docker** | 本机没装（见第 7 章环境事实），且第一版不需要 |
| **Redis / MQ / ES** | 没有对应场景。全文检索用 MySQL 内置 FULLTEXT 即可 |
| **前端** | 先 CLI/HTTP 验证能力，前端是最后的包装 |

> **纪律：要加任何东西，必须有理由并写进本文档。** 评估标准是「它解决了哪个具体问题、带来了多少可测量的提升」，而不是「它很流行」。

### 4.3 与既有项目的复用边界

从作者此前的后端项目里**借鉴设计范式，但不照搬实现**：

| 借鉴 | 不照搬 |
|---|---|
| **可降级装配的范式**：未配置时只 `log.warn` 不抛异常、绝不阻断 Spring 启动、提供 `enabled()` 供调用方判断 | **配置存储方式**：那个项目把 AI 配置存进内嵌 SQLite 的 `setting` 表、经 `SettingController` 读写 —— 那是它「零配置文件」的产品定位要求的。本项目是独立服务，**用标准 `@ConfigurationProperties` + 环境变量占位** |
| **四维预算治理**（轮次/时长/token/成本） | 其具体业务逻辑 |
| 统一返回体与全局异常处理的思路 | 直接复制代码（两个仓库无共享依赖，各自实现） |

## 5. 分阶段实施计划

> **每一步都必须以 commit + push 结束**，提交信息三段式（problem → change → verification），
> 实测数字写进提交正文。工作量是估算，实测后回填。

### 第 0 步：建仓与选型验证

| 项 | 内容 |
|---|---|
| **目标** | 打通工程骨架，验证三个技术前提（解析器 / LLM 通道 / 框架版本） |
| **产出** | Maven 工程骨架、`docs/verification-log.md` 首条记录 |
| **验证 1 · 解析器** | 用 JavaParser 解析**中性公开语料**（reggie 外卖 79 文件 / 4,070 行；Tomcat examples 70 文件 / 7,282 行）：统计成功文件数 / 失败文件数 / 失败原因分布，**记录解析成功率与耗时** |
| **验证 2 · 框架版本** | Boot 4.1.1 + JavaParser 3.28.2 + mysql-connector 能否共存并启动（冲突则退 3.5.x 并记录原因） |
| **验证 3 · LLM 通道** | 未配 Key 时必须能正常启动（降级）；配上 Key 后跑一次最小对话并记录延迟 |

| **提交信息** | `chore: project skeleton and toolchain verification` |
| **估算** | 0.5 天 |

### 第 1 步：符号表与调用图（**不接 LLM**）

| 项 | 内容 |
|---|---|
| **目标** | 先做确定性的事 —— 这是后面所有 AI 能力的地基 |
| **产出** | 表 1–6 落库；`SymbolRetriever` 四类查询（定位 / 谁调用我 / 我调用了谁 / 有哪些实现） |
| **验证 1** | **人工抽查 10 个方法**的调用点，与 IDEA 的 Find Usages 比对，记录准确率、漏报、误报 |
| **验证 2** | 统计 `call_edge.resolved` 比例，并**列出未解析原因分布**（外部依赖 / 反射 / 动态 / 歧义） |
| **验证 3** | 记录索引耗时、内存占用、库体积（按仓库规模） |
| **判据** | 内部方法调用点准确率与 IDE 一致（差异点必须能解释）；解析失败的文件与原因被如实记录 |
| **✅ 实测结果** | reggie：79 文件 / **473 符号** / **823 调用边** / 4.4 秒；**人工抽查 10 个方法 → 9 个与 IDEA 完全一致、1 个差异已归因、假边 0**；**调用点采集完整（62 = 62）**，连边率 82.3%。详见 `verification-log.md` |
| **提交信息** | `feat: symbol table and call graph indexing` |
| **估算** | 2–3 天 |

### 第 2 步：三层检索 + 单文件问答

| 项 | 内容 |
|---|---|
| **目标** | 第一次让模型参与，但**责任限定在「组织答案」** |
| **产出** | 第 2 层全文检索（MySQL FULLTEXT + ngram）；`/api/ask` 最简版；**先只在单文件范围内问答**（缩小问题空间，好定位 bug） |
| **验证** | 拿 10 个真实问题跑，逐条人工判对错；记录 token 与延迟 |
| **判据** | 10 个问题里正确答案全部带 file+line；答错的能归因（检索没召回 / 模型组织错） |
| **提交信息** | `feat: single-file Q&A with file-and-line evidence` |
| **估算** | 1–2 天 |

### 第 3 步：扩到整仓库 + 远程仓库拉取 + 上下文预算

| 项 | 内容 |
|---|---|
| **目标** | 让问答覆盖整个仓库，同时**不把仓库塞进上下文**；并让「给个链接就能用」成立 |
| **产出 A** | 检索范围扩到全仓库；选片策略（相关性排序 + 截断 + 去重）；token 预算控制 |
| **产出 B** | **远程仓库拉取**：支持 `{gitUrl}` 入口，公开仓库直接可用 |
| **关键决策** | **用 tarball 下载，不用 `git clone`** —— ①本机实测 `github.com:443` 间歇不通，而 `codeload.github.com` / `api.github.com` 稳定（push 直连 3 次全败、走 API 才成功）；②我们只需要**某个提交的工作区快照**，不需要 git 历史，tarball 更小更快；③顺带能从 API 拿到 commit SHA，正好填 `repo.commit_hash` |
| **安全约束** | **主机白名单**（只允许 github.com 及其下载域，否则贴个内网地址就是 SSRF）、包大小上限、解压路径校验（防 zip slip）；私有仓库走环境变量里的 token，不进仓库 |
| **验证 A** | 在中等规模仓库上跑，**记录单次问答的 token 消耗与耗时分布** |
| **验证 B** | 贴一个真实 GitHub 公开仓库链接 → 拉取 → 索引 → 摘要，全程不碰命令行，记录端到端耗时 |
| **判据** | 单次问答 token 不超过配置上限；远程仓库能成功索引且 commit 号正确 |
| **提交信息** | `feat: whole-repo retrieval and remote repository fetch` |
| **估算** | 2–3 天 |

### 第 4 步：证据校验 + 定向补检索（**分水岭一**）

| 项 | 内容 |
|---|---|
| **目标** | **这一步决定它是「玩具」还是「工具」** |
| **产出** | 三层校验（①② 必须程序化，真读磁盘文件）；四类失败定向补检索；`evidenceMismatch` 计数 |
| **验证** | **故意构造幻觉**：问一个不存在的方法、诱导模型引用不存在的文件 → 看校验能否拦下；再手动篡改库里的行号，看②层能否发现 |
| **判据** | 编造的路径/行号/片段 **100% 被 ①② 层拦下**（拦截率实测并记录） |
| **提交信息** | `feat: programmatic evidence verification and targeted re-retrieval` |
| **估算** | 2 天 |

### 第 5 步：多跳调用链检索（**这一步才变成 Agent**）

| 项 | 内容 |

## 6. 评估方案

### 6.1 自动出题与自动判卷

| 题型 | 出题方式 | 判卷口径 |
|---|---|---|
| LOCATE | 随机挑方法，问「它在哪定义」 | 文件路径一致 **且** 行号区间包含定义起点 |
| CALLERS | 随机挑方法，问「谁调用了它」 | 调用点集合比（精确率/召回率/F1） |
| CALLEES | 随机挑方法，问「它调用了谁」 | 集合比 |
| STRUCTURE | 问「这个类有哪些方法/字段」 | 集合比 |
| IMPLEMENTS | 问「这个接口有哪些实现类」 | 集合比 |
| IMPACT | 问「改这个签名影响哪些调用点」 | 集合比 |

**Ground truth 全部来自静态分析结果（第 1 步的产物），不来自 LLM。**

### 6.2 指标

| 指标 | 定义 | 计算方式 |
|---|---|---|
| **命中率** | 按题型统计的正确率 | 精确匹配或集合 F1（分题型报告，不合并成单一数字） |
| **证据有效率** | 通过校验①的证据 / 总证据 | 程序化 |
| **证据一致率** | 通过校验②的证据 / 总证据 | 程序化 |
| **幻觉拦截率** | 被拦下的编造证据 / 构造的编造证据总数 | 构造 N 条不存在的问题实测 |
| **拒答率** | 模型主动拒答的比例 | 反映「知道自己不知道」 |
| **平均跳数 / 平均 token / 单条成本** | 遥测统计 | 成本意识 |

### 6.3 三组对比实验

| 对比 | 看什么 | 想证明什么 |
|---|---|---|
| 纯向量检索 vs 三层检索 | 命中率差异 | **「能算准的别猜」是对的** |
| 无证据校验 vs 有校验 | 幻觉拦截率 | 程序化校验的实际防护效果 |
| 单跳 vs 多跳 | 复杂问题命中率 / 平均跳数 / 成本 | 多跳的收益与代价 |

### 6.4 可复现性要求

- 出题用**固定随机种子**，同一 seed 必须出同一批题
- 记录 `generator_version`，题目生成逻辑变更时版本号递增
- **全量跑**，不许挑好看的题；结果如实报告，包括答错的用例
- 评估时锁定仓库版本（`commit_hash`）

## 7. 验证与测试素材

### 7.1 测试语料的选择

不同规模暴露不同问题：小仓库看正确性，大仓库看扩展性拐点。

> ⚠️ **一条硬规则：语料必须是中性的公开代码，不能拿作者自己的其它项目当素材。**
> 两个简历项目互相「分析」会产生很难解释的观感问题（看起来像互相配套、甚至像结果被安排过）；
> 而被分析的那个仓库如果本身还是 fork，更容易说不清归属。
> **测试的便利不值得拿项目叙事的干净去换。**（2026-09-17 已按此纠偏，见 `verification-log.md`）

**本机现状（已实测）**：

| 档位 | 规模 | 语料 | 状态 |
|---|---|---|---|
| 小（主素材） | 3k–10k 行 | **reggie 外卖**：79 文件 / 4,070 行，Maven + Spring Boot + MyBatis-Plus，**重度使用 Lombok** | ✅ 已索引 |
| 小（非标准布局） | 3k–10k 行 | **Tomcat 自带 examples**：70 文件 / 7,282 行，**没有 `src/main/java`** | ✅ 已索引 |
| 中 | 3–6 万行 | — | ❌ 本机为空，需下载 |
| 大 | 10 万行以上 | `E:\Java\JDK21\lib\src.zip`（**15,225 个 .java / 5,108,008 行**） | ⚠️ 是压缩包，需解压 |

**为什么是这两个**：reggie 是公开教学代码（无归属争议）、标准 Maven 结构、重度使用 Lombok
（正好压已知盲区）；Tomcat examples 没有 Maven 结构，用来测**非标准布局的健壮性**（已验证可处理）。
**两者都与作者的任何个人项目无关。**

**多语料的价值已在实测中兑现**：换语料当场就暴露了一个「一个语料永远测不出」的健壮性 bug
（`NoClassDefFoundError` 中断整次索引），详见 `verification-log.md`。
**所以语料不是够用就行，要杂** —— 每条设计决策都要在不同结构的代码上验一遍。

**建议**：

- **中规模**：用第 3 步的远程拉取功能下载一个真实开源仓库，**顺便自测 tarball 拉取路径**
- **大规模**：解压 `E:\Java\JDK21\lib\src.zip` 作**压力测试**（本地文件、无需联网、无合规风险）。
  它是模块化目录结构（`java.base/java/lang/String.java`），也顺带测非标准布局

### 7.2 准确率抽查方法（第 1 步的验证方式）

1. 从 `symbol` 表随机抽 **10 个方法**（排除 getter/setter，避免过于简单）
2. 对每个方法，用 IDEA 的 Find Usages 得到人工基准
3. 与 `call_edge` 查询结果比对，逐条记录：**命中 / 漏报 / 误报**
4. 对每个差异点给出解释（外部依赖？lambda？动态代理？）—— **解释不了的要当成 bug 追**

每次索引与问答都要记录（写进 `docs/verification-log.md`）：

| 类别 | 记录项 |
|---|---|
| 索引 | 文件数、总行数、解析成功率、耗时、峰值内存、库体积 |

## 8. 风险与已知盲区

> **原则：静态分析必然有漏，如实列出而不是假装 100% 准。**

### 8.1 静态分析盲区（JavaParser 层面）

| 盲区 | 表现 | 缓解 |
|---|---|---|
| **反射调用** | `Class.forName(...).getMethod(...).invoke(...)` 无法静态解析出目标 | 调用边记 `resolved=0` + `reason=REFLECTION`，在答案中标注「可能存在反射调用」 |
| **动态代理 / Spring AOP** | 源码里是接口调用，**实际执行的是代理增强后的方法** | 标注 `reason=DYNAMIC`；文档说明「谁调用了它」在 Spring 项目里可能失真 |
| **lambda 与匿名类** | 调用点归属的符号可能与直觉不同（属于合成方法） | 记录 `call_kind=LAMBDA`，必要时向上归属到外层方法 |
| **Lombok / 注解处理器生成代码** | getter/setter/构造器在源码里不存在，静态看不到 | 记录 `reason=LOMBOK`；对 getter/setter 类查询可提示「可能由 Lombok 生成」 |
| **泛型擦除** | 泛型参数类型在运行时丢失，静态类型推断可能不精确 | 以源码声明类型为准；影响面分析时对泛型方法标注「不确定」 |
| **跨模块/外部依赖调用** | 调用的目标不在本次索引范围内 | 记 `resolved=0` + `reason=EXTERNAL`（**与「不存在」严格区分**） |

### 8.2 Spring 项目的特殊难点

Bean 之间的调用在源码里是**接口调用**，实际实现由运行时注入决定（`@Autowired` 注入哪个实现，静态看不出来）。

**缓解**：读 `@Primary` / `@Qualifier` 标注作为启发式线索；**无法确定时明确标注「不确定」**，而不是随便选一个实现类当答案。

### 8.3 行号漂移

索引建立后源码改动 → 库里的行号失效。

**缓解**：所有证据核验都比对 **内容 hash**；发现漂移即标注该文件需重新索引，并在答案中明示「基于旧版本」。（这也是 2.4 中「证据必须真读磁盘文件」的原因 —— **永远不信上下文里的代码是当前版本**。）

### 8.4 大仓库的索引成本

十万行以上的仓库，解析耗时与内存占用会显著上升，MySQL 的符号/边表也会膨胀。

**缓解**：第 1 步就实测三档规模的数据并记录拐点；必要时加「按目录/模块增量索引」。

### 8.5 范围蔓延（最现实的风险）

**缓解**：第 1.5 节的非目标清单是硬边界；**任何新增技术组件都必须在本文档里补一条「它解决了什么问题、带来多少可测量提升」**。

## 9. 验收标准

- [ ] 静态分析（符号表 / 调用图）有**准确率抽查结果**（与 IDE Find Usages 比对 10 个方法）
- [ ] 问答输出**必定带 file + line**，没有证据的答案不许返回
- [ ] 证据校验 ①② 层**是程序化的**（真读磁盘文件比对），且**故意构造幻觉时能被拦下**（有拦截率数字）
- [ ] 多跳检索有**跳数上限 + 环检测 + 每跳带证据**
- [ ] **评估集是自动生成的、可复现的**，且**答案不来自 LLM**；规模 ≥ 200 条
- [ ] 有**至少三组对比实验**的实测数字
- [ ] **没接 LLM 时，静态分析部分照常可用**（依赖可降级，实测启动与查询）
- [ ] 解析的**边界情况与盲区被如实列出**（泛型/lambda/反射/动态代理/生成代码）
- [ ] 每个阶段一个提交，提交信息是 problem → change → verification 三段式，**实测数字在提交正文里**
- [ ] 按 README 步骤能从零跑通（含空 Key 降级路径）

| 问题 | 回答要点 |
|---|---|
| **为什么不用常规的向量 RAG？** | 代码有**强结构**。按问题类型分：定位 / 调用关系 / 类型层次是**确定性问题**，用符号表和调用图**能算准**；只有「大概在哪实现」这类模糊问题才需要语义检索。**把能算准的交给模型去猜，是设计错误** |
| **模型编造行号怎么办？** | 三层校验：① 文件与行号有效性、② 内容与 snippet 一致性 —— 这两层 **100% 程序化、零成本**；③「这段代码是否支持结论」才需要模型判。**故意构造不存在的问题实测过，拦截率见第 6 章** |
| **怎么评估效果？** | **评估集自动生成**：定位/调用/结构类题目的**正确答案是静态分析算出来的**，所以能脚本批量出题、自动判卷，规模上千条。**答案不来自模型，没有循环依赖** |
| **和 Cursor / Copilot 有什么区别？** | 它们做**补全**（在编辑器里猜下一行），本项目做**理解**（回答「在哪、为什么、改了影响什么」，且**证据可核验**），并且是**自托管 + 有量化评估**的 |
| **Agent 体现在哪？** | **多跳检索**：跳几跳、往哪跳、什么时候停，由模型决定。配套跳数上限、环检测、每跳带证据、四维预算 |
| **静态分析有什么盲区？** | **如实列出**（第 8 章）：反射、动态代理（Spring AOP 会让调用关系失真）、Lombok / 注解处理器生成的代码、泛型擦除、lambda。**并且说明怎么标注「不确定」而不是假装全准** |
| **不接模型能用吗？** | **能** —— 静态分析那两层本来就不需要 AI。这个设计让「哪部分是 AI、哪部分不是」清清楚楚（第 3.6 节） |
| **为什么没用 XXX 框架 / 中间件？** | 说明当时的权衡。**「第一版不需要向量库」这句话本身就是设计判断**，不是偷懒 |
| **为什么前端排在第 8 步、而且构建产物不提交？** | 引擎没定型就做界面等于返工 —— 接口每改一次就得重做一遍。构建产物提交进仓库则会带来「改了源码忘了重建、服务的是旧产物」这类事故（云舒NAS 上踩过）。所以：**先让 API 稳定，再让界面跟上** |
| **同类项目也有前端，你的差异在哪？** | 前端不是差异点，是**入场券** —— 没有界面，连被认真看的机会都没有。差异在**答案能不能被核验**（证据 ①② 层程序化校验）和**效果有没有量化**（评估集自动生成、答案不来自模型）。**界面让人愿意点进来，校验和评估让人留下来** |

**本项目的边界（它不声称什么）**：它不声称「能理解任何代码库」——静态分析的盲区在第 8 章如实列出，
并且用「标注不确定」而不是「假装全准」来处理；它的检索核心也不是向量 ——
因为代码有结构，**能算准的不交给模型猜**。这两条是设计立场，不是缺陷。
