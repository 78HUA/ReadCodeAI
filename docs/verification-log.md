### ❗ 换语料暴露的两个真实问题（本轮最大收获）

**问题 1：`NoClassDefFoundError` 直接中断整次索引 —— 健壮性 bug，已修**

```
java.lang.NoClassDefFoundError: com/fasterxml/jackson/core/util/DefaultPrettyPrinter$Indenter
    at ReflectionClassDeclaration.solveMethod(...)        ← JavaParser 用反射解析类路径上的类
    at MethodCallExpr.resolve(...)
    at SourceAnalyzer.resolveCall(SourceAnalyzer.java:269) ← 我们的代码
```

reggie 用 Jackson，JavaParser 反射解析它时撞上**类路径里缺失的类** → 抛 `NoClassDefFoundError`。
**它是 `Error` 不是 `Exception`**，原来的 catch 覆盖不到，**整次索引直接失败**
（reggie 的第一次索引就是失败的，仓库行留在 `INDEXING` 状态没有落成 `FAILED`）。

修法：在调用点级别接住 `LinkageError` 并归类为 `MISSING_CLASS`；同时在索引编排层也接住，
保证任何意外都能把仓库行标成 `FAILED` 而不是卡在 `INDEXING`。修完后 reggie 里此类只剩 1 条。

**启示：一个语料测不出健壮性。** 旧语料从没触发过这个分支 —— 这就是多语料的价值。

**问题 2：方法的起始行会包含注解行 —— 我对行号语义的假设错了**

测试断言「符号的起始行应包含符号名」，在 reggie 上失败：

```
RiderController#save/1 记录的起始行 86 应包含符号名，实际内容：@PostMapping
```

带注解的方法，区间起点是注解行（`@PostMapping`）。**这是对的** —— 注解本就是声明的一部分。
正确的不变式是「**记录的行区间内包含符号名**」，不是「起始行包含符号名」。

→ **给第 8 步前端的提醒**：证据卡片点开 `文件:行号` 时，可能先看到的是注解行，不是方法签名。

### 漏报的根因：已复现、结论明确（用新语料复现）

reggie 上的实例：

```
EmployeeService.java:12       R<Employee> login(HttpServletRequest request, Employee employee);
EmployeeController.java:34    return employeeService.login(request, employee);   ← 我们记成 UNSOLVED
```

**方法确实在源码里，调用点也确实存在，但我们没连上边。**

**根因**（此前的探针打出了真实异常栈）：JavaParser 解析一个方法调用时，会为候选方法构造
`MethodUsage`，而 **`MethodUsage` 的构造函数会去求该方法的返回类型与参数类型**。
`HttpServletRequest`、`StringRedisTemplate` 这类**不在我们类路径上的类型**求值即抛
`UnsolvedSymbolException`，**整个调用点的解析就此失败 —— 哪怕我们需要的信息（哪个类的哪个方法）早就够了**。

**旁证（同一机制，两种结果）**：`ApplicationConfig#getJdbcTemplate/0` 的 12 处调用全部解析成功 ——
因为它返回的 `JdbcTemplate` 恰好在我们自己的类路径上（依赖 `spring-boot-starter-jdbc`）。

**决定：现在不修。** 理由：
1. 修法（给求解器加目标仓库的依赖 jar / 受限启发式回退）成本不小，且**有引入假边的风险** ——
   对一个主张「证据可核验」的工具，**多一条错边比少一条边更糟**；
2. 第 1 步的判据是「与 IDE Find Usages 比对、差异能解释」，而**根因已经能解释了**，
   这本身就是判据要求的东西；
3. 先让抽查数据说话，再决定值不值得为召回率动手。

**留档的修复方向**（按性价比排序，将来要用直接照做）：

1. **给类型求解器加目标仓库的依赖 jar**（`JarTypeSolver`）—— 治本，但要解析该仓库的 pom 依赖树
2. **受限启发式回退**：解析失败、且接收者能确定为「本类字段 + 类型唯一指向仓库内某个类」时，
   按名字 + 参数个数找唯一匹配，命中则记为 `resolved` 但 `reason='HEURISTIC'`
   （**必须能和精确解析分开统计**，否则数字会骗人）
3. 接受现状并如实说明（当前选择）

#### 那 11 处差距是什么 —— **不是漏采集，是没连上**

```
我们的库：已连边 51 ＋ 未连边 11 ＝ 62 个调用点
IDEA    ：                          62 个调用点     ← 完全一致
```

**调用点的采集一处不漏（62 = 62）**；差的是「把调用点连到目标符号」这一步（51/62 = 82.3%）。
而且**未连上的 11 处没有消失** —— 它们在库里带着 `reason='UNSOLVED'` 完整保留。
这正是「未解析的调用必须保留原文与原因」这条设计决策的价值：
**没有它，这里就只能得出「工具漏了 11 处」这个错误结论。**

#### 根因（逐条核对过源码，11 处无一例外）

`R.success(T object)` 是**泛型方法** —— JavaParser 必须求出**实参类型**才能推断类型参数 `T`。
而这 11 处的实参类型**全部牵连到不在类路径上的外部类**：

| 实参写法 | 实参类型 | 结果 |
|---|---|---|
| `R.success(pageInfo)`（7 处） | `Page<Rider>` / `Page<Orders>` —— MyBatis-Plus 外部类 | ❌ 解析失败 |
| `R.success(addressBookMapper.selectList(qw))` | mapper 是 `BaseMapper` 派生接口，泛型牵连外部类型 | ❌ |
| `R.success(ordersService.pageOrders(...))` | 返回 `Page<Orders>` | ❌ |
| `R.success(dishDtoPage)` / `pageDto` / `mealDtoPage` / `stats` | 同上家族 | ❌ |
| **对照**：`R.success(addressBook)` | `AddressBook`（仓库内类型） | ✅ 解析成功 |
| **对照**：`R.success("注册成功")` | `String`（JDK 类型） | ✅ 解析成功 |

**与上一节那个漏报案例是同一个病根**：JavaParser 解析调用时要做类型推断/匹配，
一旦牵涉它解不开的类型（**返回类型或实参类型**），整个调用点就失败 ——
哪怕「这个调用打到了哪个方法」本身并不需要那个类型。

修复方向与前面留档一致：给类型求解器补上目标仓库的**依赖 jar**（治本），
或对泛型方法的实参做**容错推断**（解不开就当 `Object`，只用于选方法、不用于判定边的正确性）。

#### 抽查还暴露了生成器的一处瑕疵

清单里「我们找到 **51** 个调用点」那行有多余换行，是生成脚本的 SQL 输出带尾换行所致。
不影响阅读，下次生成清单时修掉。

| reggie | 473 | **473** | SYMBOL **394**（= 212 字段 + 180 方法 + 2 构造器）+ FILE_HEADER **79**（= 文件数） |

构成**算得出来**（473 − 53 类 − 26 接口 = 394），不是"看着对"。

### ⭐ 最有价值的一条实测：ngram 下必须用短语检索

索引用 ngram 解析器（否则中文注释整段搜不到），但 ngram 会把标识符切成二元组，
**自然语言模式在标识符上几乎全是噪声**：

| 关键词 | 自然语言模式 | **短语检索（双引号）** | LIKE（人工基准） |
|---|---|---|---|
| `loginCheck` | **307** ❌ | **1** ✅ | 1 |
| `文件上传` | 3 | **1** ✅ | 1 |
| `登录` | 8 ✅ | **8** ✅ | 8 |
| `订单` | 17 ✅ | **17** ✅ | 17 |
| `R.success` | **257** ❌ | **0** ❌ | 61 |

两个结论**直接写进了实现**（不是写在文档里就算）：

1. **一律用 `AGAINST('"词"' IN BOOLEAN MODE)` 短语检索** —— 命中数与 LIKE 人工基准一致；
   自然语言模式把 `loginCheck` 放大到 307 条，那种"检索"没法用来回答任何问题
2. **含标点的查询必须先切词** —— `R.success` 直接检索命中 **0**（标点让短语失配），
   切成 `success` 之后才正常。**所以切词是正确性的一部分，不是性能优化**

### 证据核验第三次做进测试

检索命中的 chunk，**逐条回磁盘比对该行区间的原文与 chunk 内容是否逐字一致**：

```java
String fromDisk = String.join("\n", lines.subList(hit.startLine() - 1, hit.endLine()));
assertThat(hit.content()).isEqualTo(fromDisk);
```

理由：检索结果将来要**当证据展示**，内容与行号对不上就等于证据是假的。

### ❗ 跑起来才暴露的两个 bug（设计没问题，实现有坑）

**bug 1：中文问句检索到 0 段**

问「登录检查是在哪里做的？」时检索结果为空 —— 切词器把**整句当成一个 token**
（中文没有空格，且 `Character.isLetterOrDigit` 对汉字也返回 true），
拿这一整串去做短语检索，永远命中不了。
**修法：中文按二元组切**（与 ngram 索引的粒度对齐），并加回归测试守住。
顺带加了「先精确后放宽」：短查询要求全部词命中，拿不到结果再放宽成任一词命中。

**bug 2：模型返回 `refused: null`，整条答案解析失败**

Jackson 3 **默认拒绝把 null 映射到原始类型** `boolean`，
一条本来正确的答案因为一个缺失字段就全军覆没。
**修法：解析用包装类型（宽容）+ 校验严格** —— 缺文件或行号的证据条目被丢弃并计数，
丢弃后若没有可用证据就按拒答处理（**绝不把脏数据当证据放出去**）。

> 这两条都属于「**设计没问题、实现有坑**」，而且**只有真跑才会暴露** ——
> 写单测时还不知道该断言什么。这就是「实测」不可替代的地方。

## 第 3 步（后半）：上下文预算与选片 · 2026-09-18

**产出**：`ContextSelector` —— 检索回来的块 ≠ 喂给模型的块。四条规则，每条都有理由：

| 规则 | 为什么 |
|---|---|
| **精确名提升** | 问题里的标识符与块符号名精确相同 → 排最前。**确定性加分，不是猜的** |
| **去重** | 同一位置、或内容完全相同的块（复制粘贴/生成代码）只留一个 |
| **单文件上限**（默认 3） | 否则一个到处被引用的热门文件会霸占整个上下文，把真正的答案挤出预算 |
| **预算截断** | 按 token 估算累加；单块超过预算一半则跳过（它会把别的线索全挤掉） |

外加一项：**检索候选池 = 选用块数 × 4**。固定只取 8 条时，上面这些规则**根本轮不到生效** ——
你得先多召回，选片才有东西可选。

### 实测：两个语料上的选片效果

| 语料 | 检索候选 | 采用 | 采用块的 token |
|---|---|---|---|
| reggie（小） | 11–29 段 | **8 段** | 约 1,700–2,200 |
| **gson（中）** | **32 段** | **8 段** | **约 7,000–9,000** |

**⚠️ 一个必须如实说明的发现：token 预算目前不是主要约束。**
预算配的是 30,000，而实际采用量在 reggie 上约 2,000、gson 上约 8,000 ——
**真正在起作用的是「块数上限」和「单文件上限」，预算只是安全网。**
这说明 `top-k=8` 与 `max-context-tokens=30000` 这两个默认值没有互相校准过。
**该调成多少，等第 6 步的评估数据来说话，不拍脑袋改。**

### ❗ 又修一个只有真跑才暴露的 bug：模型输出非法 JSON

```
Q8. 哪里做了图片上传？
调用失败 —— IllegalStateException: 模型返回的 JSON 无法解析：Unrecognized character escape '('
```

**小模型吐出了 `\(` 这种没转义的字符**，而当时的实现会**整题崩掉**。这不对：
模型格式错是一个**能被计数的质量指标（格式错误率）**，不是异常。

修成三层防线：
1. **剥壳**：模型爱把 JSON 包在 Markdown 代码块里，或前后加一句话
2. **修补**：把字符串里的非法转义修掉（实测最常见的一种）
3. **失败就明确归类为「模型输出格式错误」并拒答** —— 不崩、也不假装答出来了

修完 reggie 的抽查汇总从 **「9 答 1 拒 1 失败」变成「9 答 1 拒 0 失败」**。

## 第 4 步：证据校验 + 定向补检索（**分水岭一**）· 2026-09-18

### 产出

**另外**：确定性路线（STATIC）的证据**也过 ① 层核验** —— 它来自我们自己的索引，源码改动后同样会漂移。

### ⭐ 拦住了什么：逐条构造编造，看它能不能过

用 `@TempDir` 造可控仓库，**不依赖数据库与语料，永远可复现**（11 条断言）：

| 编造方式 | 结果 |
|---|---|
| 编造的文件路径 | ✅ 拦下（FILE_NOT_FOUND） |
| 越界的行号 | ✅ 拦下（LINE_OUT_OF_RANGE） |
| **文件与行号都真实、但引用的片段是编的** | ✅ **拦下**（CONTENT_MISMATCH） |
| 把真实证据的行号篡改掉 | ✅ 立刻被拦 |
| 路径越出仓库（`../../../etc/passwd`） | ✅ 拦下（PATH_ESCAPES_REPO） |

**"我能证明防护起作用"比"我加了防护"有说服力得多** —— 这几条断言就是那句话的落地。

### 🔴 真实问答里也拦下了确凿的「张冠李戴」

三个语料上的真实调用中，模型**把真实代码引到了错误的文件/行号上**（**0% 匹配**，逐条核实过）：

| 模型说 | 磁盘上实际是 |
|---|---|
| `OrderDetailServiceImpl:29-62` 里是 `Page<Orders> pageOrders` | 那是 `pageOrderDetail` —— **引成了另一个方法** |
| `CommonController:16-16` 里是 `@PostMapping("/upload")` | 第 16 行是 `import java.util.UUID;` |
| `OrdersServiceImpl:81-93` 里是 `orders.setStatus(2); // 设置为已送达状态` | 那句话**在另一个文件里**（RiderOrderController） |

**→ 这三个如果没被拦下，就会作为"带证据的答案"返回给使用者**，而使用者点开证据会看到完全不相干的代码。

### ⚠️ 代价必须如实说：抽查从「9 答 1 拒」变成「7 答 3 拒」

| | 加校验前 | 加校验后 |
|---|---|---|
| 给出答案 | 9 | **7** |
| 拒答 | 1 | **3**（其中 1 条是"支付宝"的正确拒答，**2 条是证据没过核验**） |

**丢掉的两条，正是模型给错位置证据的题。这是正确的取舍：宁可拒答，也不把错位置的证据当正确证据给你。**
—— 而这恰好是整个项目的立场：**证据可核验，不可核验就不给。**

### 判据调了两次，每次都靠数据（记录过程，因为它说明"该严到什么程度"没有标准答案）

| 迭代 | 判据 | 结果 |
|---|---|---|
| 第 1 版 | 引用必须是磁盘区间的**连续子串** | ❌ **误杀**：模型引用时**省略中间几行**（如跳过 javadoc），是常见做法而非编造 |
| 第 2 版 | **逐行**必须全部能在区间里找到 | ❌ 仍误杀：模型会**重排、合并行**，导致个别行对不上 |
| 第 3 版（现行） | **比例判据**：≥50% 的引用行能在区间里找到 | ✅ **干净分开**：真正的错位引用是 **0% 匹配**，排版差异是大部分命中 |

**这一次调整的教训**：判据该多严，写代码时想不出来，**只有跑真实模型才知道**。

### ② 层的边界（诚实写明，别把它当成万能的）

**它能证明的**：引用的代码**大体在那个区间里**。
**它不能证明的**：那段代码**支持这个结论** —— 那是第 ③ 层的事（需要模型判或人工抽检，成本高且有误判）。

这也是为什么第 ③ 层不能省：前面两个语料上各出现过一次「结论听起来对、引的代码也真实、但那段代码并不支持这个结论」的情况。

## 第 6 步：评估集自动构造 + 自动判卷（**分水岭二**）· 2026-09-18

**命令**：`mvn -B test -Dtest=EvalRunnerTest -Dreadcodeai.verify.repo=<语料>`
**总测试**：**70 个全绿**

### 产出

| 组件 | 做什么 |
|---|---|
| `QuestionGenerator` | 从索引**随机取样出题**（5 种题型），**标准答案由静态分析算出** |
| `AutoGrader` | 自动判卷：定位题看"包不包含"，集合题算精确率/召回率/F1 |
| `EvalRunner` | 出题 → 逐题作答 → 判卷 → 分题型出指标 |
| `question` / `eval_run` 表 | 题库与运行汇总（第 7、8 张表，数据模型到此齐了） |

**判卷口径全项目统一成一种位置键** `文件:起始行` —— 于是判卷就是纯粹的集合比较，
不需要为每种题型写一套比较逻辑。**答案来自静态分析、不来自 LLM，所以没有"用模型判模型"的循环依赖。**

### 实测

| 语料 | 题目数 | 命中 | 命中率 | 平均耗时 | LLM 调用 |
|---|---|---|---|---|---|
| **gson**（中规模，1,700 符号） | **211** | 211 | **100%** | 12 ms/题 | **0 次** |
| reggie（小，477 符号） | 95 | 95 | **100%** | 8 ms/题 | **0 次** |

分题型（gson）：LOCATE 50/50 · CALLERS 50/50 · CALLEES 50/50 · STRUCTURE 50/50 · IMPLEMENTS 11/11

**可复现**：测试断言「同一 seed 出完全相同的题、换 seed 出不同的题」。
`IMPLEMENTS` 在 gson 上只有 11 道 —— 受语料限制（要有"接口 + 至少一个实现类"才能出题），**不是生成器的问题**。

### ⚠️ 这个 100% 必须打星号，否则就是自欺

**题从索引出、答案也从索引答 —— 同源。** 所以 100% 是**按构造**的，它**不是**"准确率"。

**它是回归套件**：任何让确定性管线丢信息、走错路的改动，都会立刻在这里掉分。
它的价值不在于那个数字好看，而在于**掉分时能立刻指出哪里断了**。

**开放问答的准确率不在这套里** —— 那由人工判定的抽查来量（第 2 步：10 题判对 9、正确拒答 1）。
**两边分开报**；把两者混成一个"准确率"才是真正会骗人的做法。

### ⭐ 它立刻就赚回了成本：抓出 3 个真 bug

命中率的爬升轨迹就是这三个 bug 的修复过程：

| 阶段 | 整体命中 | 抓出的问题 | 修法 |
|---|---|---|---|
| 首跑 | **22.2%** | 答案**无条件把目标符号塞进证据**，于是集合题永远多一个元素 → 集合题全部 0 命中（F1 却高达 0.96，这个矛盾是关键线索） | 只在结果为空时才用目标兜底 |
| 修复后 | **84.8%** | **裸方法名歧义**：题目只写"read 方法"，gson 里一堆 `read`，路由挑到了另一个 → 答案与真值**零重叠**（F1 恰好等于命中率，暴露了这一点） | 题目带上归属类名 + 路由学会**限定类内查找** |
| 再修 | **93.6%** | **同名重载**（参数个数不同）与**同名类**让问题本身没有唯一答案 | 歧义题不出（那种题连人都答不准） |
| 再修 | **100%** | **单字符类名提取不出来**：reggie 的核心类就叫 `R`，而标识符正则要求 ≥3 字符 → 问题直接掉进语义检索 | 候选放宽到任意长度，**让符号表去过滤** |

**其中两个是真产品 bug，不只是评估的毛病**：
- 裸方法名歧义 → 真实用户问"谁调用了 read 方法"时，我们也会给他另一个 `read`
- 单字符类名 → 问 `R` 的任何问题都会退化成语义检索（而在没配 LLM 时直接报错）

## 第 5 步：多跳调用链检索（**这一步才变成 Agent**）· 2026-09-19

**命令**：`mvn -B test -Dtest=AgentLoopTest,ToolsTest,AgentServiceTest,MultiHopComparisonTest -Dreadcodeai.verify.repo=<语料>`
（真实模型那组另跑：`source notes/llm-env.sh` 后 `mvn -B test -Dtest=MultiHopLiveTest`）
**总测试**：**109 个全绿**（4 个跳过：网络用例与语料相关的可选断言）

### 产出

| 组件 | 做什么 |
|---|---|
| `AgentLoop` | **手写的 tool-calling 循环**：模型每轮输出一个 JSON —— 调工具或给结论；我们执行工具、把结果拼回上下文 |
| `ToolRegistry` + 6 个工具 | `findDefinition` / `findCallers` / `findCallees` / `findImplementations` / `readSymbol` / `textSearch` |
| `SymbolResolver` | 名字 → 真实符号。**歧义时不猜**，把候选还回去让模型限定 |
| `VisitedEdgeSet` | 环检测：同一条边不重复走（键 = 工具名 + 规范化参数） |
| `BudgetGuard` | 四维预算：轮次 / 时长 / token / 成本，任一超限即停并记下是哪一个 |
| `AgentService` + `/api/agent` | 三岔路口：确定性问题不经模型、语义问题单跳、链式问题多跳。`mode=single|multi` 可切换（对比实验就靠它） |
| `ChainQuestionGenerator` | 链式问题的**自动出题 + 静态真值**（调用图反向 BFS，N 跳内的全部上游） |

**为什么工具是确定性的**：模型决定"查什么"，工具决定"事实是什么"。这条分工是多跳不会变成幻觉放大器的前提 ——
每一跳的证据都来自索引与磁盘，**不是模型复述出来的**。

### 实测一：机制（离线脚本模型 · 完全确定 · 毫秒级）

用脚本化的假模型把每条兜底路径单独走一遍 —— 这些是确定性逻辑，用真模型测会变成"网络好的时候能测、每次花钱、还不可复现"。

| 要证明的事 | 结果 |
|---|---|
| 能沿调用图一跳一跳走完，结论带**通过核验**的证据 | ✅ 42 跳走满，上游集合覆盖静态真值 |
| 重复的边不再执行，且明确告知模型 | ✅ 第 2 次相同调用被拦下，工具只执行 1 次 |
| 连续重复 → 主动终止 | ✅ 第 4 轮停机（NO_PROGRESS），不会把 10 轮预算烧完 |
| 轮次耗尽 → 在有限轮内停下，且**轨迹不丢** | ✅ 第 4 轮（保留给结论的那一轮）停机，轨迹证据一并交出 |
| token 预算单独生效 | ✅ 每次 1000 token、上限 2500 → 第 3 轮后停机（BUDGET_TOKENS） |
| 证据对不上磁盘 → 退回一次 → 仍不行就拒答 | ✅ 2 轮后 EVIDENCE_REJECTED |
| 模型胡言乱语 → 重发一次提示 → 归类为格式错误，不崩 | ✅ 2 轮后 FORMAT_ERROR |
| 结论没有任何证据 | ✅ NO_EVIDENCE 拒答 |

**预算语义（写成规则，因为它会让人算错轮次）**：轮次上限 N 表示最多 N 次模型调用，
其中**最后一轮保留给结论**（模型在这一轮若还要求调工具，直接停机并交出轨迹）。
所以 N 轮最多能查 N-2 次。

### 实测二：第三组对比实验（**单跳 vs 多跳**）

链条问题：「沿调用链向上追：有哪些方法（直接或间接，最多 2 跳）最终会调用 X？」
**真值 = 调用图反向 BFS 的结果**（不是人标的、也不是模型判的），
两边都换算到同一个口径上算召回：**证据位置落在哪个调用点上 → 就算找到了那个上游方法**。

**离线（理想模型脚本 —— 量尺自检，不是效果证据）**

| 目标方法 | 真值 | 单跳(同题) | 单跳(最强) | 多跳 | 跳数 | 轮次 |
|---|---|---|---|---|---|---|
| `GsonTypes#requiresOwnerType/1` | 5 | 0% | 40% | **100%** | 3 | 4 |
| `Gson#fieldNamingStrategy/0` | 2 | 0% | 0% | **100%** | 2 | 3 |
| `ISO8601Utils#padInt/3` | 3 | 0% | 33% | **100%** | 2 | 3 |

平均：单跳(最强) **24.4%** → 多跳 **100%** · 平均跳数 2.33 · 累计 8,738 token · 18 ms/题。
**100% 是按构造的**：脚本走的就是真值那条路。它证明的是"量尺与循环机制正确"，**不是"模型能力强"**。

**真实模型（智谱 glm-4-flash · gson 语料 · 3 题 · 轮次上限 8）**

| 目标方法 | 真值 | 单跳(最强) | 多跳 | 跳数 | 轮次 | token | 终止原因 |
|---|---|---|---|---|---|---|---|
| `GsonTypes#requiresOwnerType/1` | 5 | 40% | 60% | 4 | 7 | 9,234 | BUDGET_ROUNDS |
| `Gson#fieldNamingStrategy/0` | 2 | 0% | **100%** | 3 | 5 | 6,254 | FINAL |
| `ISO8601Utils#padInt/3` | 3 | 33% | **100%** | 3 | 7 | 12,988 | FINAL |

平均：单跳(最强) **24.4%** → 多跳 **86.7%** · 平均跳数 3.67 · 平均轮次 6.33 ·
累计 **28,476 token** · **30.8 s/题** · 拒答 1 题。

**五次真实运行（同一配置）的波动，如实记录**：

| 运行 | 召回（三题） | 平均召回 | 终止原因 | 结论 |
|---|---|---|---|---|
| 1 | 40% / 50% / 100% | 63.3% | 3×NO_PROGRESS | 0/3 |
| 2 | 60% / 50% / 100% | 70.0% | BUDGET / NO_PROGRESS / BUDGET | 0/3 |
| 3 | 60% / 100% / 100% | 86.7% | EVIDENCE_REJECTED / NO_PROGRESS / NO_PROGRESS | 0/3 |
| 4 | 60% / 100% / 100% | 86.7% | BUDGET / FINAL / BUDGET | 1/3 |
| 5 | 60% / 100% / 100% | 86.7% | BUDGET / FINAL / FINAL | 2/3 |

**判据达成情况**：多跳完整度显著高于单跳上限（24.4% → 63–87%），
且**五次运行全部在预算内终止**（无失控、无抛异常）。✅

### ⚠️ 这两个数字必须分开说，否则就是自欺

**86.7% 是"查到了"的完整度，不是"答出来了"的完整度。**
多跳的召回按**轨迹里查到的证据**算（那些调用点确实被查出来了、也过了核验），
而五次运行里 15 道题只有 **3 道**最终形成了带证据的结论（其余在预算内被拦下，轨迹保留）。

**结论率低的原因已经定位**：模型不知道轮次上限时会**一路查下去**，直到被闸门掐断 ——
它不是在偷懒，而是在"把能查的都查完"。修复动作（都已生效，运行 4–5 的结论率因此升到 1/3 → 2/3）：
每轮提示剩余轮次、最后一轮只允许给结论、重复时把"还没查过的上游"算给它看、附上证据写法样例。
**它是小模型 + 重协议的现实**：结论那支要求嵌套 JSON 与 evidence 数组，比工具调用那支复杂，模型会本能地回避。
所以"结论率"是下一步最该改的指标，而不是召回率。

### ⭐ 真实模型这一跑，抓出 4 个真 bug（两个会让整次问答崩掉）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 整次问答抛 `InvalidPathException` 崩掉 | 模型把行号写进 `file` 字段（`"...Factory.java:144"`），而 **Windows 路径不允许冒号** | 解析宽容：`文件:行号` / `文件:起-止` 自动拆开；核验层再兜一层（非法路径 = 一条不合格证据，而不是异常） |
| 2 | 所有涉及**构造器**的查询都落空 | `SymbolResolver.clean()` 把 `<init>` 的尖括号当"装饰"删掉，于是真名对不上 | `<init>` 例外；另外接受 `$` 写法（`Outer$Inner` = `Outer.Inner`） |
| 3 | 工具给出的证据**过不了自家核验** | 工具把源码读成**带行号**的文本给模型，模型照抄行号进 snippet → ②层判"内容对不上"。**工具层与核验层自相矛盾** | 工具的证据不带行号（观察里仍带，模型需要）；核验层同时容忍模型抄进来的行号前缀 |
| 4 | 英文语料上「中文问句 + 标识符」命中 0 条 | `TextRetriever` 截断到 8 个 token 时按出现顺序切，**中文二元组把类名/方法名挤掉了** | 截断时优先保 ASCII 标识符（二元组只是"够用的中文切分"，标识符才是精确线索） |

**第 3 个最值得记**：它不是模型的问题，是**我们自己两个部件的约定不一致** ——
只有真跑（工具 → 模型 → 核验）才会暴露，单测各自都是绿的。

### 顺带修的测试卫生问题（不算产品 bug，但会掩盖问题）

  指定的语料上 —— 换语料就跑红（或静默跳过）。已改成**从语料里取符号**，任何语料都能跑。

### 已知边界与局限（如实列，别当成没问题）

1. **结论率**：真实模型 15 道题只有 3 道给出结论（见上）。
2. **精度未做对照**：多跳的取证口径（调用点为证据）与单跳（检索块为证据）粒度不同，
   本轮只比了召回，**精确率没有可比口径**，故未报。
3. **MySQL ngram 全文索引的一个边界（实测）**：含 InnoDB 停用词二元组的词会命中 0 条 ——
   `main`（ma/ai/**in**）短语检索 0 条，而 `content LIKE '%main%'` 有 23 段；
   `read` 222 条、`Gson` 278 条、`static` 388 条、reggie 的 `success` 62 条都正常。
   **归因**：ngram 把词切成二元组后套停用词表，落在停用词上的整词被丢掉。
   影响有限（符号层与 LIKE 仍能覆盖），但**必须记下来**，否则以后会被当成"检索坏了"。
4. **工具证据未截断的是 subjects**：给模型看的观察有上限（20 条），给机器看的 subjects 不截断 ——
   两者口径不同是刻意的（一个受上下文预算约束，一个是事实），但也意味着"轨迹发现集合"比"模型看到的"大。
5. **`bfsPlan` 是理想顺序**：离线实验用它当"理想模型"的脚本，真实模型未必按这个顺序走，所以两者数字不可混用。

## 补记：摘要语义部分的缓存 · 2026-09-19

**起因**：实测发现原来**每看一次「② 概览」都要真调一次模型**（切一次页签 13–15 秒），
因为前端组件是 `v-if` 挂载的，切页签即重新请求；后端也没有任何缓存。

### 改法（按"结构要新鲜、语义可缓存"分开处理）

| 部分 | 处理 | 理由 |
|---|---|---|
| 结构（规模/模块/枢纽…） | **每次现算，不缓存** | 实测 83 ms；且索引一变它就必须变 |
| 语义（每个模块一句话） | **按「仓库 + 索引版本 + 模型名」缓存到 `repo_summary` 表** | 一次真实模型调用 13–15 秒，同一份索引上重复生成纯属浪费 |

**缓存键为什么是三项**：少任何一项都会给错东西 —— 换索引 → 说明是给旧代码写的；
换模型 → 那是另一次生成的结果。重新索引会删掉 `repo` 行（外键级联清掉缓存），索引时间戳再兜一层。
**缓存必须是可见、可控的**：接口返回 `cached / generatedAt / token 用量`，界面上直接标出"这份说明来自缓存（生成于 …，本次没有调用模型）"，并提供「重新生成」按钮。

### 实测（gson 语料 · 同一进程）

| 请求 | 耗时 |
|---|---|
| 第 1 次（无缓存，真调模型） | **14.4 s** |
| 第 2 次（命中缓存） | **0.097 s** |
| 第 3 次（命中缓存） | 0.085 s |
| `refresh=true`（强制重新生成） | 13.0 s |

**命中缓存后快约 150 倍**；结构部分与语义部分一起返回，所以整个概览页从 14 秒变成"眨眼之间"。
**换索引即失效**（重新索引后第 1 次仍要等十几秒）—— 这是设计要的行为，不是缺陷。

### 测试（`SummaryCacheTest`，用脚本模型数调用次数）

| 断言 | 结果 |
|---|---|
| 第一次真调模型；第二次**模型调用次数不增加**、`cached=true` | ✅ |
| `refresh=true` 强制重新生成（次数 +1） | ✅ |
| 换索引版本 / 换模型名 → 查不到旧缓存 | ✅ |
| `semantics=false` 时既不生成也不缓存 | ✅ |

**顺带补的缺口**：摘要语义的 token 用量以前没记日志，现在会打出来
（`prompt N + completion M token`）—— "花了多少"这件事，答案与摘要都该能报出来。

### ⭐ 最值钱的发现：**证据全对，结论全错**

第 5 次审查里，模型给 `SemanticSummarizer` 的 4 条意见**证据条条通过核验**，但内容：

| 模型说的 | 实际（我读代码核对） |
|---|---|
| 「catch RuntimeException 太宽泛且什么都不做」 | **错**：那段代码记了 warn 日志并返回了说明性结果 |
| 「logger 是 static 且没有关闭」 | **错**：SLF4J 的 logger 不需要关闭 |
| 「describe 可能因 repo/structure 为 null 而 NPE」 | **错**：两个都是必填入参 |
| 「类名不符合类的命名习惯」 | 无意义 |

**这正好回答了判据里那句"说明『代码理解』比『读 diff』难在哪"**：
难在最后一步 —— **「这段代码支持这个结论吗」只能靠人或另一个模型判**。
程序能核验的只有前两层：「这行代码存在」「模型是从给它的材料里引的」。
所以这一版把这条边界**写进了返回里**（`caveat` 字段），不让使用者误以为"过了核验 = 结论成立"：

> 模型意见只核验了『引用的代码真实存在、且在本材料范围内』；**『这段代码是否真的支持这条结论』本版没有程序化核验**（③ 层未实现），请自己判断。

### 过程中修的三处（都是实测逼出来的）

1. **空 catch 判定的假阳性**：`catch (E e) {` 括号在行尾、内容在下一行时，只看"括号后为空"会把**有日志的 catch** 也判成空的。假阳性比漏报更伤人（会让人不再信规则）。已改成往后找到第一行有内容的代码再判断。
2. **丢弃理由太笼统**：原来只说"没过核验"，看不出是"引了材料外的位置"还是"行对不上磁盘"。现在分开写，并带上具体位置 —— 审查工具的诊断信息必须能直接判断。
3. **格式崩了就重发同样的提示没用**：实测这个免费模型输出"多条意见 + 每条带证据"时经常坏（7 次里 3 次）。改成**定向降级**：第二次只给一段材料、只要一条意见；同时把材料上限从 400 行收到 250 行（400 行时 3 次里 2 次读超时）。

### 尚未完成 / 边界

- **审查还没有前端页面**：接口可用，四页产品流程里没加"审查"页签（模型意见质量还不值得占据一个页签，规则部分更适合先看）。
- **材料只覆盖单个类**：跨文件的一致性问题（如上表第二行）天然看不见；要做需要"类 + 它的直接协作者"的合并材料。
- **③ 层校验未实现**：这是本步骤最明确的缺口，且已被实测证明会真实误导。
- **免费模型的输出稳定性**：JSON 格式坏、空数组、读超时三种失败在 7 次里出现 5 次；换更大的模型是最直接的改法（成本换稳定）。
