### ❗ 换语料暴露的两个真实问题（本轮最大收获）

**问题 1：`NoClassDefFoundError` 直接中断整次索引 —— 健壮性 bug，已修**

```
java.lang.NoClassDefFoundError: com/fasterxml/jackson/core/util/DefaultPrettyPrinter$Indenter
    at ReflectionClassDeclaration.solveMethod(...)        ← JavaParser 用反射解析类路径上的类
    at MethodCallExpr.resolve(...)
    at SourceAnalyzer.resolveCall(SourceAnalyzer.java:269) ← 我们的代码
```

reggie 用 Jackson，JavaParser 反射解析它时撞上**类路径里缺失的类** → 抛 `NoClassDefFoundError`。
**它是 `Error` 不是 `Exception`**，原来的 catch 覆盖不到，**整次索引直接失败**
（reggie 的第一次索引就是失败的，仓库行留在 `INDEXING` 状态没有落成 `FAILED`）。

修法：在调用点级别接住 `LinkageError` 并归类为 `MISSING_CLASS`；同时在索引编排层也接住，
保证任何意外都能把仓库行标成 `FAILED` 而不是卡在 `INDEXING`。修完后 reggie 里此类只剩 1 条。

**启示：一个语料测不出健壮性。** 旧语料从没触发过这个分支 —— 这就是多语料的价值。

**问题 2：方法的起始行会包含注解行 —— 我对行号语义的假设错了**

测试断言「符号的起始行应包含符号名」，在 reggie 上失败：

```
RiderController#save/1 记录的起始行 86 应包含符号名，实际内容：@PostMapping
```

带注解的方法，区间起点是注解行（`@PostMapping`）。**这是对的** —— 注解本就是声明的一部分。
正确的不变式是「**记录的行区间内包含符号名**」，不是「起始行包含符号名」。

→ **给第 8 步前端的提醒**：证据卡片点开 `文件:行号` 时，可能先看到的是注解行，不是方法签名。

### 漏报的根因：已复现、结论明确（用新语料复现）

reggie 上的实例：

```
EmployeeService.java:12       R<Employee> login(HttpServletRequest request, Employee employee);
EmployeeController.java:34    return employeeService.login(request, employee);   ← 我们记成 UNSOLVED
```

**方法确实在源码里，调用点也确实存在，但我们没连上边。**

**根因**（此前的探针打出了真实异常栈）：JavaParser 解析一个方法调用时，会为候选方法构造
`MethodUsage`，而 **`MethodUsage` 的构造函数会去求该方法的返回类型与参数类型**。
`HttpServletRequest`、`StringRedisTemplate` 这类**不在我们类路径上的类型**求值即抛
`UnsolvedSymbolException`，**整个调用点的解析就此失败 —— 哪怕我们需要的信息（哪个类的哪个方法）早就够了**。

**旁证（同一机制，两种结果）**：`ApplicationConfig#getJdbcTemplate/0` 的 12 处调用全部解析成功 ——
因为它返回的 `JdbcTemplate` 恰好在我们自己的类路径上（依赖 `spring-boot-starter-jdbc`）。

**决定：现在不修。** 理由：
1. 修法（给求解器加目标仓库的依赖 jar / 受限启发式回退）成本不小，且**有引入假边的风险** ——
   对一个主张「证据可核验」的工具，**多一条错边比少一条边更糟**；
2. 第 1 步的判据是「与 IDE Find Usages 比对、差异能解释」，而**根因已经能解释了**，
   这本身就是判据要求的东西；
3. 先让抽查数据说话，再决定值不值得为召回率动手。

**留档的修复方向**（按性价比排序，将来要用直接照做）：

1. **给类型求解器加目标仓库的依赖 jar**（`JarTypeSolver`）—— 治本，但要解析该仓库的 pom 依赖树
2. **受限启发式回退**：解析失败、且接收者能确定为「本类字段 + 类型唯一指向仓库内某个类」时，
   按名字 + 参数个数找唯一匹配，命中则记为 `resolved` 但 `reason='HEURISTIC'`
   （**必须能和精确解析分开统计**，否则数字会骗人）
3. 接受现状并如实说明（当前选择）

#### 那 11 处差距是什么 —— **不是漏采集，是没连上**

```
我们的库：已连边 51 ＋ 未连边 11 ＝ 62 个调用点
IDEA    ：                          62 个调用点     ← 完全一致
```

**调用点的采集一处不漏（62 = 62）**；差的是「把调用点连到目标符号」这一步（51/62 = 82.3%）。
而且**未连上的 11 处没有消失** —— 它们在库里带着 `reason='UNSOLVED'` 完整保留。
这正是「未解析的调用必须保留原文与原因」这条设计决策的价值：
**没有它，这里就只能得出「工具漏了 11 处」这个错误结论。**

#### 根因（逐条核对过源码，11 处无一例外）

`R.success(T object)` 是**泛型方法** —— JavaParser 必须求出**实参类型**才能推断类型参数 `T`。
而这 11 处的实参类型**全部牵连到不在类路径上的外部类**：

| 实参写法 | 实参类型 | 结果 |
|---|---|---|
| `R.success(pageInfo)`（7 处） | `Page<Rider>` / `Page<Orders>` —— MyBatis-Plus 外部类 | ❌ 解析失败 |
| `R.success(addressBookMapper.selectList(qw))` | mapper 是 `BaseMapper` 派生接口，泛型牵连外部类型 | ❌ |
| `R.success(ordersService.pageOrders(...))` | 返回 `Page<Orders>` | ❌ |
| `R.success(dishDtoPage)` / `pageDto` / `mealDtoPage` / `stats` | 同上家族 | ❌ |
| **对照**：`R.success(addressBook)` | `AddressBook`（仓库内类型） | ✅ 解析成功 |
| **对照**：`R.success("注册成功")` | `String`（JDK 类型） | ✅ 解析成功 |

**与上一节那个漏报案例是同一个病根**：JavaParser 解析调用时要做类型推断/匹配，
一旦牵涉它解不开的类型（**返回类型或实参类型**），整个调用点就失败 ——
哪怕「这个调用打到了哪个方法」本身并不需要那个类型。

修复方向与前面留档一致：给类型求解器补上目标仓库的**依赖 jar**（治本），
或对泛型方法的实参做**容错推断**（解不开就当 `Object`，只用于选方法、不用于判定边的正确性）。

#### 抽查还暴露了生成器的一处瑕疵

清单里「我们找到 **51** 个调用点」那行有多余换行，是生成脚本的 SQL 输出带尾换行所致。
不影响阅读，下次生成清单时修掉。

|---|---|---|---|
| reggie | 473 | **473** | SYMBOL **394**（= 212 字段 + 180 方法 + 2 构造器）+ FILE_HEADER **79**（= 文件数） |

构成**算得出来**（473 − 53 类 − 26 接口 = 394），不是"看着对"。

### ⭐ 最有价值的一条实测：ngram 下必须用短语检索

索引用 ngram 解析器（否则中文注释整段搜不到），但 ngram 会把标识符切成二元组，
**自然语言模式在标识符上几乎全是噪声**：

| 关键词 | 自然语言模式 | **短语检索（双引号）** | LIKE（人工基准） |
|---|---|---|---|
| `loginCheck` | **307** ❌ | **1** ✅ | 1 |
| `文件上传` | 3 | **1** ✅ | 1 |
| `登录` | 8 ✅ | **8** ✅ | 8 |
| `订单` | 17 ✅ | **17** ✅ | 17 |
| `R.success` | **257** ❌ | **0** ❌ | 61 |

两个结论**直接写进了实现**（不是写在文档里就算）：

1. **一律用 `AGAINST('"词"' IN BOOLEAN MODE)` 短语检索** —— 命中数与 LIKE 人工基准一致；
   自然语言模式把 `loginCheck` 放大到 307 条，那种"检索"没法用来回答任何问题
2. **含标点的查询必须先切词** —— `R.success` 直接检索命中 **0**（标点让短语失配），
   切成 `success` 之后才正常。**所以切词是正确性的一部分，不是性能优化**

### 证据核验第三次做进测试

检索命中的 chunk，**逐条回磁盘比对该行区间的原文与 chunk 内容是否逐字一致**：

```java
String fromDisk = String.join("\n", lines.subList(hit.startLine() - 1, hit.endLine()));
assertThat(hit.content()).isEqualTo(fromDisk);
```

理由：检索结果将来要**当证据展示**，内容与行号对不上就等于证据是假的。

### ❗ 跑起来才暴露的两个 bug（设计没问题，实现有坑）

**bug 1：中文问句检索到 0 段**

问「登录检查是在哪里做的？」时检索结果为空 —— 切词器把**整句当成一个 token**
（中文没有空格，且 `Character.isLetterOrDigit` 对汉字也返回 true），
拿这一整串去做短语检索，永远命中不了。
**修法：中文按二元组切**（与 ngram 索引的粒度对齐），并加回归测试守住。
顺带加了「先精确后放宽」：短查询要求全部词命中，拿不到结果再放宽成任一词命中。

**bug 2：模型返回 `refused: null`，整条答案解析失败**

Jackson 3 **默认拒绝把 null 映射到原始类型** `boolean`，
一条本来正确的答案因为一个缺失字段就全军覆没。
**修法：解析用包装类型（宽容）+ 校验严格** —— 缺文件或行号的证据条目被丢弃并计数，
丢弃后若没有可用证据就按拒答处理（**绝不把脏数据当证据放出去**）。

> 这两条都属于「**设计没问题、实现有坑**」，而且**只有真跑才会暴露** ——
> 写单测时还不知道该断言什么。这就是「实测」不可替代的地方。

## 第 3 步（后半）：上下文预算与选片 · 2026-09-18

**产出**：`ContextSelector` —— 检索回来的块 ≠ 喂给模型的块。四条规则，每条都有理由：

| 规则 | 为什么 |
|---|---|
| **精确名提升** | 问题里的标识符与块符号名精确相同 → 排最前。**确定性加分，不是猜的** |
| **去重** | 同一位置、或内容完全相同的块（复制粘贴/生成代码）只留一个 |
| **单文件上限**（默认 3） | 否则一个到处被引用的热门文件会霸占整个上下文，把真正的答案挤出预算 |
| **预算截断** | 按 token 估算累加；单块超过预算一半则跳过（它会把别的线索全挤掉） |

外加一项：**检索候选池 = 选用块数 × 4**。固定只取 8 条时，上面这些规则**根本轮不到生效** ——
你得先多召回，选片才有东西可选。

### 实测：两个语料上的选片效果

| 语料 | 检索候选 | 采用 | 采用块的 token |
|---|---|---|---|
| reggie（小） | 11–29 段 | **8 段** | 约 1,700–2,200 |
| **gson（中）** | **32 段** | **8 段** | **约 7,000–9,000** |

**⚠️ 一个必须如实说明的发现：token 预算目前不是主要约束。**
预算配的是 30,000，而实际采用量在 reggie 上约 2,000、gson 上约 8,000 ——
**真正在起作用的是「块数上限」和「单文件上限」，预算只是安全网。**
这说明 `top-k=8` 与 `max-context-tokens=30000` 这两个默认值没有互相校准过。
**该调成多少，等第 6 步的评估数据来说话，不拍脑袋改。**

### ❗ 又修一个只有真跑才暴露的 bug：模型输出非法 JSON

```
Q8. 哪里做了图片上传？
调用失败 —— IllegalStateException: 模型返回的 JSON 无法解析：Unrecognized character escape '('
```

**小模型吐出了 `\(` 这种没转义的字符**，而当时的实现会**整题崩掉**。这不对：
模型格式错是一个**能被计数的质量指标（格式错误率）**，不是异常。

修成三层防线：
1. **剥壳**：模型爱把 JSON 包在 Markdown 代码块里，或前后加一句话
2. **修补**：把字符串里的非法转义修掉（实测最常见的一种）
3. **失败就明确归类为「模型输出格式错误」并拒答** —— 不崩、也不假装答出来了

修完 reggie 的抽查汇总从 **「9 答 1 拒 1 失败」变成「9 答 1 拒 0 失败」**。

和人工快速扫读（结论听起来对）。**这是第 4 步 ③ 层校验必要性的第二次实证。**

## 第 4 步：证据校验 + 定向补检索（**分水岭一**）· 2026-09-18

**命令**：`source notes/llm-env.sh && mvn -B test` → **63 个测试全绿**

### 产出

| 组件 | 做什么 |
|---|---|
| `EvidenceVerifier` | **① 文件与行号有效性**（文件在不在、行号越不越界、路径有没有越出仓库）+ **② 片段一致性**（真读磁盘比对）+ ③ 层的接口位（默认不启用） |
| `EvidenceRepair` | **按失败类型定向修正**：行号越界 → 按"发给模型的片段"修正；路径写短 → 后缀匹配；**修正后必须再过一遍校验**（不能因为"我修过"就当通过） |
| 模型契约 | 新增 `snippet` 字段：要求**逐字引用**，并明确告诉它**"我们会拿它去磁盘核对"** |

**另外**：确定性路线（STATIC）的证据**也过 ① 层核验** —— 它来自我们自己的索引，源码改动后同样会漂移。

### ⭐ 拦住了什么：逐条构造编造，看它能不能过

用 `@TempDir` 造可控仓库，**不依赖数据库与语料，永远可复现**（11 条断言）：

| 编造方式 | 结果 |
|---|---|
| 编造的文件路径 | ✅ 拦下（FILE_NOT_FOUND） |
| 越界的行号 | ✅ 拦下（LINE_OUT_OF_RANGE） |
| **文件与行号都真实、但引用的片段是编的** | ✅ **拦下**（CONTENT_MISMATCH） |
| 把真实证据的行号篡改掉 | ✅ 立刻被拦 |
| 路径越出仓库（`../../../etc/passwd`） | ✅ 拦下（PATH_ESCAPES_REPO） |

**"我能证明防护起作用"比"我加了防护"有说服力得多** —— 这几条断言就是那句话的落地。

### 🔴 真实问答里也拦下了确凿的「张冠李戴」

三个语料上的真实调用中，模型**把真实代码引到了错误的文件/行号上**（**0% 匹配**，逐条核实过）：

| 模型说 | 磁盘上实际是 |
|---|---|
| `OrderDetailServiceImpl:29-62` 里是 `Page<Orders> pageOrders` | 那是 `pageOrderDetail` —— **引成了另一个方法** |
| `CommonController:16-16` 里是 `@PostMapping("/upload")` | 第 16 行是 `import java.util.UUID;` |
| `OrdersServiceImpl:81-93` 里是 `orders.setStatus(2); // 设置为已送达状态` | 那句话**在另一个文件里**（RiderOrderController） |

**→ 这三个如果没被拦下，就会作为"带证据的答案"返回给使用者**，而使用者点开证据会看到完全不相干的代码。

### ⚠️ 代价必须如实说：抽查从「9 答 1 拒」变成「7 答 3 拒」

| | 加校验前 | 加校验后 |
|---|---|---|
| 给出答案 | 9 | **7** |
| 拒答 | 1 | **3**（其中 1 条是"支付宝"的正确拒答，**2 条是证据没过核验**） |

**丢掉的两条，正是模型给错位置证据的题。这是正确的取舍：宁可拒答，也不把错位置的证据当正确证据给你。**
—— 而这恰好是整个项目的立场：**证据可核验，不可核验就不给。**

### 判据调了两次，每次都靠数据（记录过程，因为它说明"该严到什么程度"没有标准答案）

| 迭代 | 判据 | 结果 |
|---|---|---|
| 第 1 版 | 引用必须是磁盘区间的**连续子串** | ❌ **误杀**：模型引用时**省略中间几行**（如跳过 javadoc），是常见做法而非编造 |
| 第 2 版 | **逐行**必须全部能在区间里找到 | ❌ 仍误杀：模型会**重排、合并行**，导致个别行对不上 |
| 第 3 版（现行） | **比例判据**：≥50% 的引用行能在区间里找到 | ✅ **干净分开**：真正的错位引用是 **0% 匹配**，排版差异是大部分命中 |

**这一次调整的教训**：判据该多严，写代码时想不出来，**只有跑真实模型才知道**。

### ② 层的边界（诚实写明，别把它当成万能的）

**它能证明的**：引用的代码**大体在那个区间里**。
**它不能证明的**：那段代码**支持这个结论** —— 那是第 ③ 层的事（需要模型判或人工抽检，成本高且有误判）。

这也是为什么第 ③ 层不能省：前面两个语料上各出现过一次「结论听起来对、引的代码也真实、但那段代码并不支持这个结论」的情况。
